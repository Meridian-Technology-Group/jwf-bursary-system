# Item 5: DNS / Resend domain setup instructions in the admin guide

> Source: `docs/backlog/post-demo-change-list.md` — item 5. Status: Not started.

The Foundation wants to send bursary emails from their own domain rather than a shared/default sender, which requires verifying the sending domain in Resend and publishing the associated DNS records (SPF, DKIM, DMARC). This is a documentation-only task: add a section to the admin/operations guide that walks a non-developer through the Resend domain-verification process and the DNS records to create, so the Foundation can complete (or brief their IT provider to complete) the setup without engineering involvement.

## Story 5.1 — DNS / Resend domain setup documented in the admin/operations guide
**As a** Foundation administrator (Charlotte) or her IT provider, **I want** a written, step-by-step guide to verifying the sending domain in Resend and adding the required DNS records, **so that** the system can send bursary emails from the Foundation's own domain with good deliverability, without needing a developer.

**Acceptance criteria**
- [ ] Given the documentation set, When looking for email-domain setup, Then a dedicated section exists in the admin/operations guide (e.g. a new `docs/operations/resend-domain-setup.md`, cross-linked from `docs/guides/admin-assessor-guide.md` and the operations index) with a clear title and stated audience (admin + IT provider).
- [ ] Given the guide, When read start to finish, Then it explains the goal (send from the Foundation's own domain, improve deliverability) and the prerequisites (access to the Resend dashboard for the shared JWF account; ability to edit DNS records for the sending domain / access to whoever manages DNS).
- [ ] Given the guide, When following the Resend steps, Then it walks through adding and verifying a domain in the Resend dashboard (Domains → Add Domain), including choosing the region and the sending subdomain convention (e.g. `send.` / `mail.`), with a note or placeholder for a screenshot.
- [ ] Given the guide, When configuring DNS, Then it documents each required record type — **SPF** (TXT), **DKIM** (the CNAME/TXT records Resend generates), and **DMARC** (TXT `_dmarc` record) — explaining what each is for in plain language and that the exact host/value strings must be copied from the Resend dashboard (records are account/domain-specific and must not be hard-coded in the doc).
- [ ] Given the guide, When adding records at a DNS provider, Then it explains where records go (host/name vs value/target), the typical propagation wait, and that the record host may need the provider's domain suffix stripped or appended depending on the registrar.
- [ ] Given the guide, When verification is triggered, Then it describes how to confirm the domain shows **Verified** in Resend and what a pending/failed state looks like, with a short troubleshooting list (records not propagated, duplicate/ conflicting SPF record, wrong host, proxied/greyed CNAME).
- [ ] Given the guide, When setup is complete, Then it states the required follow-up in this system: set the "from" sender to the verified domain via the relevant environment variable(s), and that changing env vars is a user-approved deployment step (per `CLAUDE.md` / `docs/operations/environment-variables.md`) — and it cross-references that env-vars doc rather than duplicating it.
- [ ] Given the guide, When read, Then it notes the JWF-specific reality that one shared Resend account/key is used across both Vercel scopes and that `RESEND_WEBHOOK_SECRET` is Production-scope only (consistent with existing operations docs), so domain verification is done once for the shared account.
- [ ] Given the guide, When a maintainer sanity-checks it, Then all referenced dashboard paths and DNS record types match current Resend behaviour at time of writing and any values shown are clearly marked as illustrative placeholders, not literal records to paste.

**Notes / dependencies**
- Documentation only — no product code, no schema, no migration.
- Preferred home: `docs/operations/` (alongside `deployment.md`, `environment-variables.md`, `waf-auth-rate-limiting.md`), cross-linked from the admin/assessor guide (`docs/guides/admin-assessor-guide.md`) so a non-technical admin can find it. Match the existing operations-doc tone and structure.
- Do **not** paste real DNS record values into the doc — they are domain/account-specific and generated by Resend; instruct the reader to copy them live from the dashboard.
- The actual sender domain (e.g. the exact subdomain) and the DNS provider are Foundation decisions — leave clearly marked placeholders and flag as an open question for Charlotte where a concrete value is needed.
- Related config context already captured in project memory / existing docs: single shared Resend environment, Production-only webhook secret, `APP_URL`/sender env vars — reuse and link, don't restate.
- Definition of done is reviewability: someone unfamiliar with Resend can complete verification by following the guide, and it points them at the (user-approved) env-var change needed to actually send from the new domain.
